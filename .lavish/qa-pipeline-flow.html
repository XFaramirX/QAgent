QA Automation Pipeline

A fully automated, GitHub-native QA system. A Product Manager opens an issue — no manual steps needed. AI agents capture a live page snapshot, extract acceptance criteria, generate Playwright tests, and open a structured pull request for human review. Every action is traceable through git history, workflow logs, and PR discussions.

Stage 0 — Issue Submission & Triage

issue template qa-ticket.yml

A PM opens a GitHub Issue using the QA Ticket form. The form collects Target URL, Feature Title, Description, and Acceptance Criteria. On submit, GitHub automatically applies the qa-pending label — no manual step needed.

labels: [qa-pending] ← applied by the template automatically

workflow qa-triage.yml

Fires immediately on issues: [labeled, edited]. Makes a single fast AI call (temperature 0, max 512 tokens) to check completeness. Re-fires every time the PM edits the issue, so incomplete tickets get a second chance automatically.

What the AI checks
  • Description is non-trivial (≥ 2 sentences or bullet points)
  • At least one acceptance criterion (line starting with - or numbered)
  • Target URL is present, or an explicit note that it is not yet available

✅ Pass path

Removes qa-pending, applies qa-ready, also removes needs-more-info if present. Posts a progress table comment on the issue showing all pipeline stages as ⏳ Queued. The qa-ready label immediately triggers issue-to-qa.yml.

⚠️ Fail path

Applies needs-more-info. Posts a comment listing exactly what's missing with one actionable suggestion per gap. The PM edits the issue — this re-triggers the triage check automatically (no label shuffling needed).

Stages 1–5 — QA Pipeline

Triggered by qa-ready label or workflow_dispatch from the Actions tab.

1 Setup — Branch isolation & ticket scaffold

Derives a canonical Ticket ID (QA-NNN from the issue number) and a branch name (qa/qa-NNN-issue-NNN). Creates the branch, pushes it, then runs ci-create-ticket.js to scaffold tickets/QA-NNN/ticket.md from the issue body. Commits and pushes.

Branch isolation means every issue lives on its own branch — broken AI output never touches main until a human approves the PR.

# Automatic for issues:
TICKET_ID = "QA-007"
BRANCH = "qa/qa-007-issue-7"
# Manual dispatch inputs:
ticket-id: "QA-007"
issue-number: "7"
target-url: "https://..."
Commits use github-actions[bot] identity — every artifact is traceable to a run ID.

2 Snapshot — Live page evidence capture

Runs npm run snapshot -- <URL> <ticketId> using Playwright in headless Chromium. Captures the full page state as a bundle of artifacts committed to the ticket branch.

This step is non-fatal — if the URL is unreachable (e.g. behind auth, not yet live), the pipeline continues and the Analyst records it as a risk. Only real evidence is used; AI agents are forbidden from inventing UI behaviour.

File Purpose
snapshot.md Accessibility tree — source of truth for locators
page.html Full DOM (fallback locator reference)
page.png Full-page screenshot
console.log Console errors & warnings
network.log Network request list
meta.json URL, title, viewport, capturedAt

3 Requirement Analyst — AI-driven acceptance criteria extraction

Runs ci-run-analyst.js. Uses the Requirement Analyst system prompt from .github/agents/requirement-analyst.agent.md (same prompt as the VS Code agent — CI is a headless execution of the same instructions).

Sends the ticket content + snapshot accessibility tree to the GitHub Models API. Writes analysis.json containing scenarios, risks, questions, assumptions, and a snapshotRef.

Retry & resilience

Retries up to 3× with exponential backoff (5s → 10s → 15s) on any HTTP error or JSON parse failure.

Uses response_format: json_object to prevent prose leaking into the output.

Falls back to GITHUB_TOKEN if no AI_API_KEY secret is set.

What the analyst MUST NOT do
  • Invent business rules not in the ticket
  • Fabricate error messages or field limits
  • Invent API behaviour or user permissions
  • Generate test data without evidence

Uncertainties go into questions; reasonable inferences go into assumptions with a confidence level.

4 Playwright Generator — Test generation & validation

Runs ci-run-generator.js with the Playwright Generator system prompt. Reads analysis.json and the snapshot bundle. The accessibility tree (snapshot.md) is the single source of truth for locators — no invented selectors allowed.

Also auto-copies analysis.json → approved-analysis.json for CI (the PR review is the real human gate). Runs npm run test:ticket non-fatally — a red result still produces the PR so the reviewer can investigate.

Locator priority order
  1. page.getByRole()
  2. page.getByLabel()
  3. page.getByPlaceholder()
  4. page.getByText()
  5. page.getByTestId()
  6. CSS selector (last resort only)
Forbidden: random classes, nth-child, brittle XPath, page.waitForTimeout()

5 Open PR — Structured pull request with all artifacts

Runs ci-build-pr-body.js to assemble a rich PR body from the ticket artifacts — scenario list, test run summary, traceability table, and a reviewer checklist. Creates the PR with labels qa-automated and needs-review, assigned to the original issue author. Posts a comment on the issue with the PR link and next steps.

6 Escalation — Automatic human notification on failure

Runs only when any upstream stage fails. Posts a structured comment on the source issue listing exactly which stages failed, a direct link to the workflow run, and retry instructions. Applies the escalation-needed label so maintainers can filter for issues needing attention. A failed snapshot is not escalated — it's expected for unreachable URLs.

PR Gates — Validation & Review

required check Plan structure & traceability

  • ticket.md exists
  • analysis.json is valid JSON
  • Required fields present: ticketId, feature, scenarios
  • Scenarios array is non-empty
  • snapshotRef set (warning if missing)
  • At least one .spec.ts in generated/
  • approved-analysis.json exists (warning if missing)
Exit code 1 on errors → PR cannot merge.

required check TypeScript spec typecheck

Runs npx tsc --noEmit on all spec files. Catches type errors in generated tests before they reach main — no browser needed, runs in under 10 seconds.

CODEOWNERS Required human review

.github/CODEOWNERS requires at least one approved review from a named team or owner before any tickets/ change merges. This is the primary safety gate — AI output is never auto-merged.

/tickets/ → @YOUR_TEAM
/.github/ → @YOUR_USERNAME
/scripts/ → @YOUR_USERNAME

Label Lifecycle

Label Applied by Means Triggers
qa-pending Issue template (on submit) Ticket submitted, triage not yet run qa-triage.yml
needs-more-info qa-triage.yml (fail path) Ticket incomplete — PM needs to edit Nothing (waits for PM to edit issue)
qa-ready qa-triage.yml (pass path) Triage passed, pipeline starting issue-to-qa.yml
qa-automated issue-to-qa.yml (on PR) PR opened by the pipeline —
needs-review issue-to-qa.yml (on PR) PR awaiting human review —
escalation-needed issue-to-qa.yml (escalate job) Pipeline failed — human intervention needed —

Repository Setup Checklist

Create in Settings → Labels. The pipeline uses these names exactly.

qa-pending qa-ready needs-more-info qa-automated needs-review escalation-needed

Branch Protection on main

Settings → Branches → Add rule for main:

  • Require status check: QA plan structure & traceability
  • Require status check: TypeScript spec typecheck
  • Require approving review (min 1, from CODEOWNERS)
  • Dismiss stale reviews on new commits
